# Защита от дублей поставщиков и НДС после парсинга

**Дата:** 2026-08-31  
**Статус:** Задача 2 (НДС после парсинга) — ✅ завершена (сверка 2026-09-15). Задача 1 (автодополнение поставщиков) — не реализована, опциональна.  
**Приоритет:** Высокий

---

## Контекст

Система загрузки прайс-листов имеет две проблемы:

1. **Дубли поставщиков**: Один и тот же прайс можно загрузить под разными названиями поставщика (`supplier_external_id`), создавая дублирующие записи в БД
2. **НДС при загрузке**: Сейчас `vat_rate_percent` указывается при загрузке файла, но правильнее — после парсинга, когда пользователь видит результат

---

## Проблема 1: Защита от дублей поставщиков

### Текущее поведение

**Версионирование в рамках одного поставщика работает корректно:**
- `supplier_external_id="Рога и Копыта"` → version 1, 2, 3...
- Цены переписываются, актуальная версия используется в калькуляциях

**Проблема — разные названия:**
- Пользователь загружает прайс: `supplier_external_id="Рога и Копыта"` → создаётся Supplier A
- Пользователь загружает тот же прайс: `supplier_external_id="РогаКопыта"` → создаётся Supplier B
- **Результат:** два разных поставщика с одинаковым прайсом в БД

### Решение: Автодополнение имени поставщика в UI

**Цель:** Предотвратить создание дублей через подсказки при вводе

**Как работает:**
1. Пользователь начинает вводить имя поставщика: `"Рога..."`
2. UI запрашивает `/api/v1/suppliers/search?q=Рога`
3. Бэкенд возвращает список похожих поставщиков:
   ```json
   [
     {"external_id": "Рога и Копыта", "name": "Рога и Копыта ООО", "version_count": 5},
     {"external_id": "Рогаикопыта", "name": "Рога и Копыта", "version_count": 2}
   ]
   ```
4. UI показывает dropdown с подсказками
5. Пользователь **выбирает существующего** → не создаётся дубль

---

### Варианты реализации

#### **Вариант A: Prefix match (простой)**

**Трудоёмкость:** 🟢 **2-3 часа**

**Бэкенд:**
- Новый эндпоинт `GET /api/v1/suppliers/search?q={query}`
- SQL: `WHERE external_id LIKE 'query%' OR name LIKE 'query%'`
- Возвращает до 10 совпадений

**Фронтенд:**
- Поле ввода с автодополнением (combobox/autocomplete)
- Debounce 300ms перед запросом
- Показ подсказок в dropdown

**Плюсы:**
- Простая реализация
- Быстрый поиск по индексу

**Минусы:**
- Не находит опечатки: "Рога и Копыта" vs "Рага и Копыта"
- Не находит перестановки: "Копыта и Рога"

---

#### **Вариант B: Fuzzy match (умный)**

**Трудоёмкость:** 🟡 **4-6 часов**

**Бэкенд:**
- Эндпоинт `GET /api/v1/suppliers/search?q={query}`
- PostgreSQL: `pg_trgm` расширение для similarity search
- SQL: `WHERE similarity(name, 'query') > 0.3 ORDER BY similarity DESC`

**Фронтенд:**
- Тот же UI, что в варианте A

**Плюсы:**
- Находит опечатки и вариации написания
- Более "умный" поиск

**Минусы:**
- Требует PostgreSQL расширение `pg_trgm`
- Медленнее на больших объёмах (нужен GIN индекс)

---

#### **Вариант C: Нормализация + exact match**

**Трудоёмкость:** 🟡 **3-4 часа**

**Бэкенд:**
- Добавить колонку `normalized_name` в таблицу `suppliers`
- При создании поставщика: `normalized_name = normalize(external_id)` (lowercase, убрать пробелы/спецсимволы)
- Поиск: `WHERE normalized_name LIKE normalize(query) + '%'`

**Фронтенд:**
- Тот же UI

**Плюсы:**
- Находит вариации без пробелов: "Рога и Копыта" = "РогаиКопыта"
- Быстрый поиск по индексу

**Минусы:**
- Не находит опечатки
- Требует миграцию для добавления колонки

---

### Рекомендация для защиты от дублей

**Вариант A (Prefix match)** — начать с него:
- Простой и быстрый
- Покрывает 80% случаев
- Можно улучшить до Варианта B/C позже

## Проблема 2: НДС после парсинга (текущая задача)

### Текущее поведение

**Что не так:**
1. Поле `vat_rate_percent` указывается **при загрузке файла** (форма upload)
2. Если цены в прайсе **уже с НДС**, а пользователь укажет `vat_rate_percent=22%` → двойное применение НДС
3. Парсер определяет `vat_mode` ("с НДС" / "без НДС"), но пользователь не видит эту подсказку до завершения парсинга

**Правильная логика:**
1. Загрузка файла → парсинг → статус `parsed`
2. **Пользователь видит результат парсинга** + подсказку парсера (`vat_mode`)
3. **Пользователь указывает входной НДС** (обязательно): 0%, 10%, 22%, "без НДС"
4. Переход в статус `validated` → можно использовать в калькуляциях

---

### Решение: Обязательный шаг "Укажите НДС" после парсинга

**Изменения в workflow:**

```
Загрузка файла
    ↓
Парсинг (определение vat_mode — подсказка)
    ↓
[НОВЫЙ ШАГ] Укажите входной НДС ← БЛОКИРОВКА без выбора
    ↓
validated → калькуляции
```

async def update_price_import(
    import_id: uuid.UUID,
    vat_rate_percent: str | None = None,
    session: AsyncSession = Depends(get_session),

    """Обновить НДС после парсинга"""

  (0/10/22), резюмирует Celery-задачу и backfill-ит ставку в уже

- гейт `VAT_RATE_REQUIRED` стоит первым в `_quality_gate`
  (`backend/app/import_service.py:242`) — без ставки импорт не проходит

  Исходная рекомендация «vat_mode — только подсказка» устарела;
- опциональная агрегация `vat_mode` в `_status_dto` не делалась —
  осталась заглушка `vat_mode=None` (`backend/app/api/price_imports.py:175`);

  VAT-шаг через UI (ставка 22%, backfill во все значения цен).

## Комментарии для человека

- **Версионирование — это нормально**: Если пользователь загрузил прайс дважды → version 2 — это ОК
- **Дубли поставщиков — проблема**: Один прайс под разными названиями → плохо, нужно автодополнение
- **НДС после парсинга — логичнее**: Пользователь видит результат парсинга + подсказку → принимает решение
- **vat_mode — только подсказка**: Не использовать в расчётах, только показать пользователю
