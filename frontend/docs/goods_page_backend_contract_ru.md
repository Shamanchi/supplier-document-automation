# Страница «Товары»: backend-контракт и необходимые доработки

Дата актуализации: 16 августа 2026 года.

## 1. Назначение

Страница «Товары» отображает разобранные строки прайсов из backend. Frontend
не обращается к базе данных напрямую и не формирует SQL-подобные запросы.
Единственный источник данных страницы — HTTP API backend `/api/v1`.

Текущая сущность страницы — `SupplierPriceItem`, то есть позиция конкретной
версии прайса поставщика. Это ещё не дедуплицированный корпоративный справочник
уникальных товаров.

## 2. Что уже хранится в backend

В базе данных существуют:

- `supplier_price_items` — позиции разобранных прайсов;
- `suppliers` и `price_versions` — поставщик и версия источника позиции;
- `price_files` — метаданные исходного файла и ключ объекта в хранилище;
- `supplier_categories` — исходные категории поставщиков;
- `global_categories` — общий project-scoped справочник категорий;
- `supplier_category_mappings` — явное соответствие категории поставщика общей
  категории;
- `supplier_price_item_attribute_values` — извлечённые типизированные
  характеристики;
- `attribute_definitions` — словарь кодов, типов и единиц характеристик.

Для позиции ручная категория `manual_category_id` имеет приоритет над
категорией, полученной через supplier mapping.

Сам бинарный файл не хранится в PostgreSQL. Backend сохраняет его в MinIO, а в
базе данных хранит метаданные и ключ объекта. Frontend не должен обращаться к
MinIO напрямую или получать постоянный публичный URL.

## 3. Уже доступный API

### Список товаров

`GET /api/v1/price-items`

Поддерживаемые параметры:

- `query` — подстрока до 255 символов;
- `supplier_id` — точный UUID поставщика;
- `price_version_id` — точный UUID версии прайса;
- `limit` — от 1 до 200;
- `offset` — неотрицательное смещение.

`query` сейчас выполняет регистронезависимый поиск по:

- исходному наименованию товара;
- исходному артикулу;
- названию поставщика;
- имени исходного файла.

Ответ:

```json
{
  "total": 1,
  "items": [
    {
      "id": "uuid",
      "source_name": "Наименование",
      "article": "ABC-123",
      "unit": "шт",
      "category": {
        "source_path": "Категория поставщика",
        "global_category_id": "uuid",
        "global_path": "Общая / Категория",
        "mapping_status": "mapped"
      },
      "attributes": [
        {
          "code": "voltage",
          "name": "Напряжение",
          "value_kind": "decimal",
          "value": "12",
          "raw_value": "12 В",
          "unit": "В",
          "parse_status": "parsed"
        }
      ],
      "supplier_id": "uuid",
      "supplier_name": "Поставщик",
      "price_version_id": "uuid",
      "version_no": 3,
      "version_status": "active",
      "filename": "price.xlsx",
      "imported_at": "2026-08-16T00:00:00Z"
    }
  ]
}
```

Ресурс требует JWT, использует `X-Project-ID` и возвращает только позиции
выбранного проекта.

### Список поставщиков

`GET /api/v1/suppliers`

Используется для выпадающего списка поставщиков. Возвращает `id`, `code`,
`name`, число версий и краткую информацию об активной версии.

Важно: этот список сейчас глобальный и не ограничивается `X-Project-ID`.

### Категории

`GET /api/v1/catalog/categories`

Возвращает project-scoped общий справочник категорий и счётчики товаров.
Категория уже присутствует в DTO товара, поэтому её можно отображать.

### Оригинал исходного прайса

`GET /api/v1/price-versions/{price_version_id}/original`

Endpoint отдаёт сохранённый оригинал через backend с проверкой JWT и project
scope. В DTO товара уже присутствуют `price_version_id` и `filename`, поэтому
для ссылки на исходник не требуется прямой доступ к базе данных или MinIO.

Для форматов, которые браузер не умеет показывать, операция будет фактически
скачиванием файла. Полноценный inline-preview разных офисных форматов является
отдельной задачей.

## 4. Реализуемый frontend-срез

Страница использует только существующие операции:

1. Получает поставщиков через `GET /suppliers`.
2. Получает товары через `GET /price-items`.
3. Передаёт `query`, `supplier_id`, `limit`, `offset`.
4. Показывает наименование, артикул, категорию, извлечённые характеристики,
   единицу, поставщика и исходный прайс.
5. Использует серверное значение `total` для пагинации.

Поиск по `query` в UI обозначается как поиск по названию или артикулу, хотя
backend также проверяет поставщика и имя файла.

Frontend не выполняет локальную фильтрацию неполной страницы результатов:
это давало бы неверные `total` и состав страниц.

## 5. Источник и ручное исправление данных

### 5.1. Ссылка в колонке «Источник»

Первый и наиболее простой вариант — заменить текстовое имя файла в колонке
«Источник» на авторизованную ссылку:

```text
price.xlsx -> GET /api/v1/price-versions/{price_version_id}/original
```

Ссылка должна открываться через общий frontend API client, чтобы сохранить
Bearer JWT, `X-Project-ID`, обработку `401` и refresh. Постоянную MinIO-ссылку
в DTO товара добавлять не следует.

Backend-доработка для базового скачивания не требуется. Нужна frontend-логика
получения `Blob`, открытия поддерживаемого браузером формата или скачивания
оригинала с именем `filename`.

### 5.2. Переход к результатам импорта

Дополнительный вариант — переход из строки товара на страницу «Поставщики» с
автоматическим выбором импорта или версии прайса, из которой получена позиция.

Для этого необходимо:

- добавить в URL страницы устойчивый параметр `price_version_id` или
  `price_import_id`;
- при открытии страницы выбрать соответствующий импорт;
- открыть его позиции и замечания;
- сохранить JWT и текущий `X-Project-ID`;
- корректно обработать отсутствие импорта в выбранном проекте.

В DTO товара уже есть `price_version_id`. Если frontend должен переходить
строго к заданию импорта, backend потребуется дополнительно вернуть
`price_import_id` либо предоставить однозначное получение импорта по версии.

Этот переход сложнее прямой ссылки на файл, но полезен для просмотра контекста
разбора: статуса, строк, замечаний и provenance.

### 5.3. Что backend уже позволяет исправлять

Backend частично поддерживает ручную работу с результатом:

- назначение общей категории товарной позиции;
- review workflow для проблемного импорта;
- исправление mapping/rule и повторное применение правила к версии прайса.

Замысел текущего review workflow — исправлять способ разбора прайса и затем
повторно получать согласованный набор позиций. Это не универсальный табличный
редактор всех извлечённых полей.

### 5.4. Чего не хватает для редактирования товара

Подтверждённого публичного контракта для произвольного изменения всех полей
позиции, включая артикул, наименование, единицу, цену и характеристики, сейчас
нет.

Для такого сценария backend потребуется:

- отдельный типизированный `PATCH`-контракт позиции;
- как минимум возможность задать или исправить артикул;
- проверка JWT, роли и `X-Project-ID`;
- валидация типов характеристик и единиц;
- сохранение ручного значения отдельно от исходного значения парсера;
- audit: кто, когда и какое значение изменил;
- явное правило, переживает ли ручная правка повторный импорт новой версии;
- API-тесты на сохранение, повторное чтение и запрет изменения чужого проекта.

Рекомендуется не перезаписывать исходные данные парсера безвозвратно. Следует
хранить provenance и ручное override-значение, которое имеет приоритет в UI.
Иначе невозможно будет отличить ошибку исходного файла от исправления
пользователя и безопасно выполнить повторный разбор.

### 5.5. Рекомендуемый порядок реализации

1. Сделать имя файла ссылкой на существующий endpoint оригинала.
2. Добавить переход по `price_version_id` к результатам нужного импорта.
3. Подключить существующий review/mapping workflow.
4. Отдельно согласовать и реализовать ручные overrides, начиная с артикула.
5. После этого расширить редактирование на остальные поля и характеристики.

## 6. Что пока не реализуется

### 6.1. Фильтр по категории

В `GET /price-items` отсутствует `global_category_id`. Получение дерева через
`GET /catalog/categories` само по себе не позволяет корректно фильтровать
серверную пагинацию.

Требуемая доработка:

- добавить optional `global_category_id: UUID`;
- добавить `include_descendants: bool = true`;
- учитывать обе схемы назначения:
  `SupplierPriceItem.manual_category_id` и
  `SupplierCategoryMapping.global_category_id`;
- при ручной категории не учитывать конкурирующий supplier mapping;
- ограничивать найденные категории текущим `X-Project-ID`;
- сохранить ответ `{total, items}`.

Рекомендуемый пример:

```http
GET /api/v1/price-items?global_category_id=<uuid>&include_descendants=true
```

### 6.2. Поиск по извлечённым параметрам

Характеристики уже возвращаются в `items[].attributes`, но текущий SQL запроса
их не фильтрует.

Минимальный следующий этап:

- добавить `attribute_query`;
- искать по `AttributeDefinition.code`, `display_name`,
  `SupplierAttributeKey.source_header`, `raw_value` и нормализованному
  скалярному значению;
- использовать `EXISTS`, чтобы join с многозначными характеристиками не
  дублировал товары и не искажал `total`;
- для `parse_status=invalid` искать только по `raw_value`;
- применить `AND` между товарными фильтрами и `attribute_query`.

Пример:

```http
GET /api/v1/price-items?attribute_query=напряжение%2012В
```

После текстового MVP рекомендуется отдельный типизированный контракт:

```json
{
  "code": "voltage",
  "operator": "eq",
  "value": 12,
  "unit": "В"
}
```

Он должен поддерживать типы `text`, `integer`, `decimal`, `boolean`, `date`,
`datetime`, `option`, а для чисел — операторы `eq`, `gte`, `lte`, `between`.

### 6.3. Актуальность и дубли версий

`GET /price-items` сейчас читает все версии прайсов. Один товар может
повторяться в старых и новых версиях.

Требуемая доработка:

- добавить `version_scope=all|active|latest`;
- не менять текущую семантику без явного решения о совместимости;
- для пользовательского каталога рекомендовать `active`, а при отсутствии
  активной версии согласовать fallback на `latest`;
- закрепить выбор версии тестами для нескольких поставщиков и проектов.

Это устраняет исторические дубли, но не создаёт канонический уникальный товар.
Дедупликация одинаковых товаров разных поставщиков относится к matching/
canonical layer и требует отдельного продуктового решения.

### 6.4. Раздельные поля поиска

Текущий `query` достаточен для первого среза. Если понадобятся точные режимы,
следует добавить optional параметры:

- `name`;
- `article`;
- `article_exact`;
- `filename`.

Не следует перегружать frontend правилами нормализации: нормализация и поиск
должны оставаться ответственностью backend.

## 7. Требования к backend-тестам

Для будущих доработок нужны API-тесты:

1. Поиск по названию и артикулу.
2. Точный `supplier_id`.
3. Общая категория, ручная категория и категория через supplier mapping.
4. Включение и исключение дочерних категорий.
5. Текстовые и типизированные характеристики.
6. Многозначная характеристика без дублей строк и искажения `total`.
7. Совместное применение фильтров через `AND`.
8. `limit/offset` и стабильная сортировка.
9. Изоляция через `X-Project-ID`.
10. `version_scope` для старой, активной и последней версии.
11. `401`, `403`, `404` для недоступного проекта или категории.

После изменения API необходимо обновить Pydantic DTO/OpenAPI, snapshot
контракта и frontend-типы. Новый отдельный endpoint для страницы не требуется:
предпочтительно расширить ресурсный `GET /price-items`.

## 8. Явно вне текущего среза

- загрузка сертификатов, паспортов и других документов товара;
- переход к карточке документа;
- полноценный поиск соответствия требованиям ТЗ;
- verdict по техническим параметрам;
- дедупликация позиций разных поставщиков в единый товар;
- редактирование и ручное подтверждение характеристик со страницы «Товары».
