# Схема связки: документ → реестр → позиция прайса

Пакет описывает **одну общую схему**, к которой приводятся три разные вещи:
запись реестра Росаккредитации, результат распознавания документа и итог их
сверки. Общие имена полей — не косметика: только так извлечённое и эталонное
можно сравнивать поштучно и показывать менеджеру расхождение.

Машиночитаемая версия — `schema.json` (генерируется из кода, тест следит,
чтобы не разъезжались).

---

## 1. Поток данных

```
скан или PDF
   │
   ├─ есть текстовый слой ──────────────► текст          (118 из 120 паспортов)
   └─ нет ─► OCR-движок по контракту ───► текст          (99 из 117 сертификатов)
                                            │
                                    extract.py
                                            │
                                   ExtractedDocument      ← что удалось прочитать
                                            │
                                    reconcile()  ◄── RegistryIndex (зеркало ФСА)
                                            │
                                     Reconciliation       ← вердикт + замена
                                            │
                                  PositionDocumentLink    ← это забирает price_loader_app
```

Ключевая мысль: **из документа нужен ровно один надёжный реквизит —
регистрационный номер сертификата**. Всё остальное приходит из реестра, где
оно чище и с актуальным статусом. Поэтому OCR решает самую лёгкую задачу из
возможных: прочитать короткую крупную строку в верхней трети бланка.

---

## 2. Модели

### `RegistryCertificate` — запись реестра

Приведена из CSV открытых данных к каноническим именам (`mapping.py`).
Ключевые поля: `registration_number` + `registration_number_key`,
`status`, `valid_until`, `manufacturer_inn`, `product_full_name`.

Главный метод — `is_alive_on(date)`:

```python
актуален ⟺ статус ∈ {Действует, Возобновлен, Продлен} И срок ≥ дата
```

**Проверять только статус нельзя.** Записи реестра хранят состояние на момент
последнего изменения, поэтому у давно не менявшихся документов статус остаётся
`Действует` спустя годы после истечения срока — в зеркале таких 16 167 из
27 405 «действующих» по пожарному регламенту.

### `ExtractedDocument` — что прочитали

Каждое значение обёрнуто в `Field[T]` с `confidence`, `page` и `bbox`:
происхождение важнее самого значения, потому что менеджеру надо показать,
откуда взялось, а низкой уверенности достаточно, чтобы не привязывать документ.

`confidence` равен `1.0` для текстового слоя и берётся из `mean_confidence`
движка для OCR.

Класс документа (`DocumentClass`) определяет, как трактовать найденный номер:

* у **сертификата** номер — его собственный идентификатор;
* у **паспорта** номер — ссылка на смежный сертификат. Это бесплатное ребро
  «изделие → сертификат»: в 44% паспортов корпуса номер напечатан в тексте и
  достаётся без единого вызова OCR.

### `Reconciliation` — итог сверки

`Verdict`: `valid` · `expired` · `suspended` · `terminated` · `not_found` ·
`unknown`. Прикладывать к КП можно только `valid` (`Verdict.attachable`).

Разделение `not_found` и `unknown` намеренное:

* `not_found` — номера нет в реестре вовсе;
* `unknown` — номер есть в общем списке (2.6 млн), но подробной карточки в
  зеркале нет, либо номер не прочитан, либо уверенность ниже порога.

Первое — сигнал проверить сам документ, второе — расширить зеркало или
прочитать документ заново. Схлопывать их в один статус значит потерять
подсказку.

### `SuccessorCandidate` — вероятная замена

Явной связи «старый → новый» реестр **не хранит**: в новой схеме связывающие
поля пусты, в старой формулировка «выдан взамен сертификата №» встречается в
сотых долях процента записей. Преемник восстанавливается эвристикой: тот же
изготовитель по ИНН + схожесть наименования продукции по Жаккару ≥ 0.3.

На размеченных случаях корпуса это даёт 11 попаданий из 15. Промахи — старые
сертификаты с родовым наименованием («Модули порошкового пожаротушения», без
модели и ТУ). Порог понижать нельзя: ложная привязка чужого сертификата
дороже, чем отсутствие любого.

**Кандидат всегда остаётся подсказкой** и никогда не подставляется
автоматически: совпадение изготовителя и похожего наименования не доказывает,
что новый сертификат покрывает именно ту модель, что стоит в позиции расчёта.

### `PositionDocumentLink` — контракт с price_loader_app

Компактная запись для колонки «ссылка на документацию»:

```json
{
  "position_ref": "line-7",
  "doc_id": "sha256:…",
  "document_url": "b24://disk/…",
  "verdict": "expired",
  "valid_until": "2024-03-13",
  "registration_number": "ЕАЭС RU С-RU.ПБ97.В.00344/22",
  "needs_manual_review": true,
  "review_reasons": ["срок действия истёк 2024-03-13", "предложена вероятная замена — требует подтверждения менеджером"],
  "successor_registration_number": "ЕАЭС RU С-RU.ПБ97.В.00539/24",
  "successor_valid_until": "2029-03-10"
}
```

`position_ref` — идентификатор строки расчёта на стороне price_loader_app;
контур OCR его не интерпретирует и возвращает как есть.

## 3. Нормализация — без неё join не сходится

`normalize.py`:

* **Омоглифы.** В номерах систематически смешаны кириллица и латиница:
  `RU С-RU.ЧС13…` (кириллическая `С`), `C-RU.НА67…`, `C-RU.HA67…`. Двенадцать
  кириллических букв (`А Е К М Н О Р С Т У Х В`) сворачиваются в латиницу.
  Без этого один сертификат распадается на три ключа. Для OCR критично вдвойне
  — движки смешивают алфавиты на коротких токенах.
* **Пробелы внутри номера.** OCR охотно вставляет их вокруг точек и дефисов,
  поэтому `ЕАЭС RU С - RU . ПБ97 . В . 00272 / 21` приводится к тому же ключу.
* **Обозначения изделий.** `ОП-4 (з) АВСЕ ПРЕМИУМ` и `ОП-4(з)-АВСЕ-01` должны
  сойтись: пробелы вокруг скобок убираются, суффиксы исполнения отбрасываются
  (они различают позиции прайса, но покрываются одним сертификатом).
* **Диапазоны.** `ОП-2, 3, 4, 5` разворачивается в отдельные обозначения —
  один сертификат покрывает десяток позиций прайса.
* **Даты.** Набор отдаёт `дд.мм.гггг` в новой схеме и ISO в старой.

## 4. Разбор набора открытых данных

`mapping.py` описывает то, что делает набор неудобным: **схема непостоянна**.
Разделитель бывает `;`, `|` и `,`; заголовки — русские или английские;
помесячные файлы 2019–2023 идут вообще без строки заголовка с фиксированным
порядком из 51 колонки; в части срезов имена колонок дополнены пробелами до
фиксированной ширины. Схема и разделитель определяются независимо друг от
друга.

Наивный парсер «один разделитель, один заголовок» молча подхватит меньше
половины файлов и будет выглядеть работающим.

`index.py` загружает уже склеенный индекс
(`fsa_registry_mirror/registry_index.csv`, 54 076 карточек пожарного сегмента,
загрузка ~2 с) и отдельный список всех 2.6 млн номеров — он нужен только чтобы
отличать «нет в реестре» от «есть, но карточки не держим».

## 5. Заполненность полей — что реально можно использовать

Замер по всем 54 076 сертификатам пожарного регламента:

| Поле | Заполнено |
|---|---:|
| `product_full_name` | 99% |
| `valid_until` | 99% |
| `product_type` | 76% |
| `product_standards` | 73% |
| `okpd2_tnved` | 57% |
| `product_designation` | 46% |
| `manufacturer_inn` | 41% |
| `blank_number` | 18% |
| `product_model` / `product_brand` / `product_article` (любое) | **1.8%** |

Отсюда практический вывод, который легко упустить: **структурных
`Модель`/`Марка`/`Артикул` в реестре практически нет.** Ключом со стороны
реестра служит `product_full_name` — тот же слитный текст, что в блоке
`ПРОДУКЦИЯ` на бланке, только чистый. Реестр избавляет от распознавания, но не
от разбора.

## 6. Полярность контура

Одно правило, из которого выведено остальное: **при сомнении не привязывать.**
Ложно приложенный к коммерческому предложению чужой или мёртвый сертификат
дороже, чем пустая ячейка с пометкой «проверить вручную».

Поэтому:

* номер не прочитан или уверенность ниже 0.6 → `unknown`, а не догадка;
* документ мёртв → вердикт и подсказка, но не автозамена;
* расхождение срока в документе и в реестре → вердикт по реестру, но
  расхождение попадает в `review_reasons`;
* **имя файла не является источником данных ни при каких условиях** — ни срок,
  ни модель, ни номер.

## 7. Файлы

| Файл | Назначение |
|---|---|
| `schema.py` | канонические модели и статусы |
| `schema.json` | та же схема машиночитаемо, для внешних потребителей |
| `export_schema.py` | генератор `schema.json` |
| `normalize.py` | омоглифы, номера, даты, обозначения, схожесть |
| `mapping.py` | колонки набора открытых данных → канонические поля |
| `index.py` | загрузка зеркала, поиск, подбор преемника |
| `reconcile.py` | сверка извлечённого с реестром, вердикт |

Смежные документы: `docs/Ф2_Реестр_сертификатов_Росаккредитации.md` (откуда
берутся данные и почему), `docs/Ф2_Извлечение_из_паспортов_и_сертификатов.md`
(что извлекать из документов).
